## The problem

My work moves through email, task management, repositories, documents and conversations with AI models. Each tool holds one part of the context. When I need to decide a project's next step, I rebuild that context by hand, and part of the reasoning is lost between sessions.

## The proposal

AI Command Center is a reading layer over the tools I already use. It gathers relevant signals, refreshes on demand and surfaces what deserves attention. It is not a full email client or a task management system. The goal is to lower the cost of resuming context, not to replace the tools.

## What already exists

A navigable interface exists, with a collapsible menu, contextual modules and an animated visual core. The prototype validates composition, hierarchy and feel. It does not read real data, persist memory or call models.

<h2 id="contexto">Context and problem</h2>

During a workday, a signal can arrive by email, show up in a task, depend on a repository and require a conversation with an AI model. None of these tools sees the whole picture. The information exists, but the context that connects one thing to another stays with me.

The cost shows up when I resume a project. I read old conversations, look for the decision that ended up in a comment and try to rebuild the reasoning. Important decisions lose their trail, and the same context is processed several times.

<h2 id="hipotese">Opportunity and product hypothesis</h2>

If the relevant context is readable in one place and refreshes on demand, I can decide with less rework and lose less reasoning between sessions.

The product does not try to replace email, tasks or repositories. It reads those signals, keeps what is relevant and surfaces what needs attention. The scope boundary is part of the hypothesis. The less the product duplicates other tools, the lower the cost of maintaining integrations and the lower the risk of showing stale information.

<Callout variant="info" title="Product hypothesis">

Context readable in one place lowers the cost of resuming projects and makes decisions easier to trace. The hypothesis has not been tested with users yet.

</Callout>

<h2 id="papel">My role and approach</h2>

There is no separate team and no user research in this case. The product comes from my own workflow, and that is an explicit limitation. The assumptions need to be reviewed before any generalization.

<h2 id="decisoes">MVP decisions</h2>

<h3 id="experiencia-primeiro">Experience before integration</h3>

Building the interface first makes it possible to test hierarchy, reading and navigation without the cost of maintaining connectors. There is a risk of a polished shell with no function. The mitigation is to state the status of each module in the interface and in this case.

<h3 id="local-primeiro">Local before cloud</h3>

The local backend in Node.js and SQLite is planned. Data stays on the device and directory access is controlled. The downside is that installation and backup depend on me, and the product is less portable than a web service.

<h3 id="refresh-sob-demanda">Refresh on demand</h3>

Refresh happens on click, not by polling. That makes call cost predictable and avoids processing the same context several times. The cost of that choice: the interface may show an older signal until the next refresh.

<h3 id="memoria-legivel">Memory in readable files</h3>

The Persistent Memory Core uses Markdown and daily files of up to 500 lines. The format is inspectable and portable, with no dependency on a proprietary database. The downside is that retrieval quality depends on file structure and the Context Engine.

<h2 id="experiencia">Experience vision</h2>

The visual core is animated and restrained, with a collapsible menu and contextual modules. The intent is for the product to feel like a reading panel, not a metrics dashboard. Legibility, accessibility and performance are criteria from the prototype onward.

The animated core is part of the interface. It does not measure intelligence, activity or analysis quality, and it should not be read as proof that the system works.

The premise is to keep data on the device. The backend would read only authorized directories, with path validation. Future integrations with Gmail, GitHub and Jira would require API authentication, minimal scopes and revocability. The threat model covers the filesystem, credentials and untrusted content. It is part of the planning, not a completed audit.

<h2 id="memoria">Memory, context and cache (planned)</h2>

The planned Persistent Memory Core uses Markdown and daily files of up to 500 lines. The Context Engine retrieves what is relevant to the current task. Cache and metrics reduce repeated processing.

None of these components is implemented. The expected benefits are context that can be recovered without manual reconstruction, inspectable memory and lower call cost. There are no gain figures to publish.

Readable files are easy to audit but require structure for retrieval. Limited daily files control size but require compaction. Cache reduces cost but may serve stale context. The date and origin of each signal need to be visible in the interface.

<h2 id="processo">Process and technical decisions</h2>

Development follows a modular architecture, with explicit contracts between interface, backend and integrations. Acceptance criteria are defined before implementation, and deliveries produced with AI agents are reviewed against them. Documentation and the threat model are part of scope, not deferred work.

This case does not claim test results, versions or application performance without verifiable evidence.

<h2 id="proximos-passos">Lessons and next steps</h2>

The central lesson is to prioritize a foundation I can inspect. A navigable interface does not prove the product, but it makes it possible to discuss hierarchy, scope and risk before investing in integrations.

Next steps, in order: local project reading, persistent memory, remote connectors and AI analysis. Each stage needs acceptance criteria and a way to verify what was delivered.

This case will be updated when those stages have evidence. Until then, the stated state is the interface prototype.
