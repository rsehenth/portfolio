## Where the idea came from

The proposal came from a real technical investigation of instability on a Windows computer. The work used system queries, event analysis, performance measurements and evidence correlation, not a sequence of generic cleanups.

That investigation revealed an opportunity: turn technical diagnostic procedures into a reusable, accessible and conservative application. SentinelCore AI starts from that problem, not from a feature designed from the top down.

## What the product proposes

A desktop application with its own backend to run technical audits, preserve history, identify anomalies and turn to artificial intelligence when it helps interpret evidence. The backend remains operational without internet access or an AI provider.

## Four main decisions

### 1. Diagnosis before optimization

The application should investigate causes, not just recommend cleanups.

### 2. Optional, economical AI

Gemini 3.1 Flash-Lite and DeepSeek V4.1 Flash-1017 are candidates for interpreting results, while the backend runs the checks. The integration is not implemented yet.

### 3. Local persistent memory

Markdown and SQLite preserve audits, dates, incidents and hardware changes.

### 4. Safety as a requirement

Fixes must use predefined procedures, explicit authorization, post-checks and reversal when technically possible.

## Current state

Project in Discovery and architectural definition. Architecture and main requirements documented. Still no executable MVP or software validation results.

## Next step

Build the deterministic diagnostic core and validate it against historical evidence and test scenarios.

<h2 id="contexto">Context and origin</h2>

The project came from the need to investigate real performance and stability problems on Windows. The investigation that originated the product was manual, conducted with system queries, event reading, measurements and evidence correlation, with Codex assisting the technical exploration.

An earlier audit identified examples such as graphics timeouts, network port exhaustion events, high committed memory usage, unexpected shutdowns and localized application failures. These findings were not detected by SentinelCore AI: they motivated the discovery and will serve as test cases for the planned backend.

<Callout variant="info" title="Relationship to the product">

The manual investigation is the origin of the product problem. SentinelCore AI has not run these detections; it proposes turning this kind of procedure into software.

</Callout>

<h2 id="problema">Product problem</h2>

Traditional optimization tools usually start with cleanups and generic tweaks. Intermittent performance and stability problems rarely resolve that way: they require investigation, evidence correlation and an understanding of causes.

The difference between identifying symptoms, detecting anomalies, finding evidence, investigating hypotheses, confirming causes and proposing safe interventions is the core of the problem. High resource usage or a large number of logged events does not necessarily mean there is a problem.

The challenge is turning technical data into reliable information. A report that mixes fact, inference and suggestion without distinction does not help anyone decide.

<h2 id="discovery">Discovery insight</h2>

The original investigation combined native Windows capabilities: CIM/WMI, Performance Counters, Event Logs, Windows Error Reporting, native hardware APIs, process analysis, network diagnostics and temporal correlation.

The main product hypothesis is that these checks can be turned into a reusable backend without depending on constant interpretation by an AI model. The backend would produce facts and correlations; AI would only step in to interpret what is complex.

<Callout variant="warning" title="Hypothesis not validated yet">

The hypothesis has not been validated across different computers, manufacturers and Windows versions. It guides the architecture, but it is not a proven result yet.

</Callout>

<h2 id="solucao">Proposed solution</h2>

SentinelCore AI is proposed as an executable Windows application. The planned scope organizes the work into three audit modes with different depth and cost.

  class="[contain:inline-size]"
  caption="Proposed audit modes, not implemented yet"
  columns={['Mode', 'Planned scope']}

    ['Full audit', 'In-depth investigation of hardware, drivers, processes, memory, storage, network and stability records.'],

The full audit is the most demanding scenario: it has to collect a lot, correlate without losing traceability and end with a report that separates what was confirmed from what remains a hypothesis.

<h2 id="arquitetura">Hybrid architecture</h2>

The architecture separates deterministic execution from AI interpretation. The backend remains operational without internet access or an AI provider; when a model is connected, it interprets evidence that has already been collected and does not run commands.

The proposed layers are:

1. .NET desktop interface.
2. Deterministic diagnostic backend.
3. Rules engine.
4. Evidence correlation.
5. Local persistent memory.
6. Optional AI assistance.
7. Controlled correction engine.
8. Technical, readable reports.

Choosing an owned backend means maintaining collectors and rules over time. It is more work than delegating all analysis to a model, but it makes behavior predictable and every conclusion traceable back to the evidence behind it.

<h2 id="hardware">Hardware Intelligence</h2>

The planned inventory module gathers what the system exposes about the machine: CPU, GPU, memory, motherboard, BIOS/UEFI, storage, monitors, network, connected devices, drivers and versions, plus the Windows version and build.

The goal is not only to list components. The inventory serves to detect changes between audits, such as a driver update, a BIOS update or a hardware change. Those changes help explain incidents that appeared afterwards.

Not every device provides every piece of information, and coverage varies by manufacturer. The product must state what it could not read instead of filling gaps with assumptions.

The Audit Freshness Engine controls how valid information is. One planned example: 30 days after the last successful full audit, the application may recommend a new audit. The interval must be configurable.

Historical records and current measurements need to be distinguished in the interface. Old data presented as current is a product error, not just a formatting one.

<h2 id="ia">Optional artificial intelligence</h2>

Two providers are considered: Gemini 3.1 Flash-Lite and DeepSeek V4.1 Flash-1017. The architecture must allow selecting the provider, and the product must remain useful without either one.

AI will be used mainly to interpret complex evidence, prioritize hypotheses, suggest permitted investigations, explain diagnoses and draft reports. The Smart Context Engine selects the relevant information and reduces the volume of data sent to the model.

<Callout variant="warning" title="No performance promises">

There are no benchmarks, proven financial savings or quality comparisons between the models. The integration is an architecture decision, still without an implementation.

</Callout>

<h2 id="seguranca">Safety and conservative fixes</h2>

This is one of the most important decisions in the product. A desktop application with system access can cause damage, so the architecture treats fixes as controlled procedures, not free commands.

- No indiscriminate Registry cleaning.
- No arbitrary execution of AI-generated commands.
- Least privilege.
- Fixes limited to a validated catalog.
- Explicit user authorization.
- Precondition checks.
- Simulation before execution.
- Recording of the previous state.
- Post-fix verification.
- Reversal when possible.

No tool capable of changing an operating system can guarantee zero risk. The goal is to reduce risk and make every intervention visible, authorized and reversible when reversal is technically feasible.

<h2 id="incidentes">Incident monitoring</h2>

Intermittent problems rarely happen while the user is staring at a report. The proposal is to let the person register an incident after noticing slowdown or instability.

The application would examine the data available around the reported time, looking for correlations with events, hardware and recent changes. Deeper captures would have limits on duration, size and system impact.

This feature is planned. There is no continuous monitoring implemented.

<h2 id="mvp">MVP scope</h2>

The MVP is planned to prove the core before widening the product surface. The first version includes: executable Windows application, hardware inventory, basic and full audits, event analysis, process analysis, performance investigation, Markdown history, local SQLite, audit validity control and structured reports.

AI integration and the correction engine can be introduced progressively. There is no release date or announced availability.

<h2 id="estado">Status and lessons</h2>

SentinelCore AI starts from a real problem, technically investigated, not from a generic optimization idea. The hybrid architecture is a product decision: it limits what AI can do in order to preserve reliability and traceability.

The central lesson so far is that the hard part is not listing symptoms, but turning technical records into reliable information. That is why the scope starts with a deterministic backend, with collectors and rules that can be inspected.

The next validation is reproducing real diagnoses with the product's own backend, using the evidence that motivated the project and controlled test scenarios.

- **Operational safety:** limited, authorized and reversible fixes.
