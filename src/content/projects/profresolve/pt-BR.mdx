## O problema

Professores produzem continuamente planos de aula, avaliações, atividades e adaptações. O ProfResolve nasceu para reduzir parte desse trabalho repetitivo, transformando uma necessidade pedagógica em material estruturado, editável e pronto para uso.

Hoje, a ideia já foi além do protótipo: o produto está disponível publicamente e já ultrapassou 1.200 usuários cadastrados organicamente.

## Da hipótese ao produto em uso

O projeto começou com uma hipótese simples: IA poderia reduzir parte do trabalho repetitivo de preparação de materiais sem tirar do professor o controle sobre o resultado.

A partir dessa hipótese, a plataforma evoluiu para um produto com múltiplos geradores de conteúdo, edição, exportação, créditos, pagamentos, jogos educacionais e mecanismos de confiabilidade para operações com LLMs.

Com mais de 1.200 usuários cadastrados e uso recorrente da plataforma, a próxima etapa não é só construir mais funcionalidades. É entender comportamento, frequência de uso, retenção e quais fluxos entregam mais valor.

## IA falha. O produto não pode falhar junto.

Uma falha do provedor não deve consumir os créditos do professor nem encerrar a tarefa. Por isso, o fluxo trata a falha como parte esperada da operação.

Confiabilidade foi tratada como requisito de produto, não como detalhe de implementação. Em nível conceitual, a estratégia inclui:

- **Cadeia de modelos:** mais de um modelo disponível para a mesma geração
- **Retries com orçamento de tempo:** tentativas adicionais dentro de um limite definido
- **Fallback entre providers:** troca de provedor quando o primário falha
- **Circuit breaker:** pausa temporária de um caminho problemático
- **Fallback de contexto:** geração degradada em vez de erro exposto ao usuário
- **Reembolso automático de créditos:** uma falha não custa crédito ao professor
- **Kill switch e recuperação:** parada e retomada em nível operacional

Parâmetros, limiares e configurações internas permanecem na implementação; os mecanismos acima descrevem a estratégia em nível conceitual.

## Quando o custo de IA vira decisão de produto

O ProfResolve usa **créditos** como unidade de consumo. Cada tipo de geração tem um custo diferente, e o preço de cada geração é uma decisão de produto, não só uma variável de infraestrutura.

<FlowDiagram

Os créditos são a interface entre custo computacional, valor percebido pelo professor e monetização. Quando o custo de um modelo muda, isso afeta diretamente o preço de uma geração e o comportamento esperado do usuário.

O custo de cada gerador precisa acompanhar a estratégia e o modelo utilizados para manter o consumo de IA visível e administrável dentro do produto.

## Nem toda evolução técnica deve permanecer no produto

**Contexto:** Streaming via SSE foi testado para melhorar a experiência de geração.

**Problema:** Falhas de parsing podiam interromper o fluxo e produzir conteúdo parcial.

**Decisão:** O projeto voltou para uma geração síncrona mais previsível, com controle de timeout mais rigoroso.

**Trade-off:** menos percepção de resposta progressiva em troca de maior previsibilidade e confiabilidade.

O rollback foi tratado como parte normal do desenvolvimento. O que importa é que o trade-off foi explícito.

## Stack e decisões de arquitetura

O ProfResolve foi construído com Next.js App Router como base unificada de frontend, rotas de API e regras de negócio. A escolha eliminou a necessidade de um servidor separado e permite colocar a lógica de geração, autenticação e créditos no mesmo processo — com 96 rotas de API organizadas por domínio.

### PostgreSQL para estado permanente. Redis para estado temporário.

O PostgreSQL armazena tudo que precisa de consistência: usuários, créditos, materiais, pagamentos, geração histórica. O acesso é feito com SQL direto via `pg` — sem ORM — o que torna cada query explícita e auditável.

O Redis (Upstash) resolve três problemas de desempenho e resiliência: cache de sessão com TTL de 30 segundos para evitar uma consulta ao banco a cada requisição autenticada; rate limiting por janela fixa via `INCR/EXPIRE` em pipeline para proteger os endpoints de geração; e invalidação do saldo de créditos após cada débito ou reembolso.

O cliente Redis usa uma camada de fallback: se o Upstash estiver indisponível, a aplicação cai automaticamente para um provider em memória com limites reduzidos, sem interromper o serviço. O trade-off é aceitar rate limits menos precisos em degradação em vez de bloquear requisições.

### Cloudflare R2 para anexos temporários dos geradores.

Professores podem enviar PDFs como contexto para alguns geradores. O fluxo usa uma URL pré-assinada gerada no servidor: o navegador faz o upload diretamente para o R2 sem passar pelo servidor da aplicação, reduzindo latência e consumo de banda.

O R2 é acessado via SDK compatível com S3 (`@aws-sdk/client-s3`) apontando para o endpoint Cloudflare. Isso permite usar as mesmas abstrações do ecossistema AWS sem depender da infraestrutura da AWS. O bucket é temporário — os arquivos são lidos durante a geração e deletados em seguida. A funcionalidade tem flag de ativação independente.

A exportação de materiais em PDF segue um caminho diferente: o servidor renderiza o HTML do material com Playwright (Chromium headless) e retorna os bytes diretamente — o R2 não está envolvido nesse fluxo.

### Better Auth com hooks de provisionamento no banco.

A autenticação usa apenas Google OAuth — sem senha local. A escolha reduz a superfície de ataque e elimina fluxos de recuperação de senha. O gerenciamento de sessão é feito com cookies HTTP-only; o cache customizado no Redis substitui o mecanismo nativo do Better Auth para permitir controle explícito sobre TTL e invalidação.

Os hooks do Better Auth no banco fazem o provisionamento automático: na criação de um usuário, o sistema atribui o plano freemium, insere o registro de créditos inicial e registra o provider. Isso garante que todo usuário autenticado tem créditos disponíveis desde o primeiro acesso, sem uma etapa de setup separada.

O controle de acesso por papel (`freemium`, `pro`, `admin`) é implementado manualmente em `rbac.ts` — o Better Auth não tem plugins de RBAC em uso. O middleware protege `/dashboard/*` e `/admin/*` via verificação de cookie, com validação completa de sessão como segunda camada opcional, controlada por feature flag.

### Vitest para contratos de API. Playwright para fluxos críticos de produto.

Os testes Vitest cobrem dois ambientes: `node` para handlers de API, serviços e utilitários do servidor; e `dom` (happy-dom) para hooks React, lógica de cliente e componentes com estado. Testes de propriedade com `fast-check` validam os endpoints de validação de payload contra entradas geradas — arrays vazios, IDs inválidos, tipos errados — garantindo que as fronteiras de entrada sejam robustas.

Os testes Playwright cobrem os fluxos que um usuário real percorre: autenticação com redirecionamento, modal de gerador, exibição de créditos, editor, materiais e cenários de erro crítico. Seguem o padrão Page Object Model. O checkout Asaas é explicitamente excluído dos testes e2e por depender de serviço externo.

A separação é intencional: Vitest valida contratos e lógica de negócio de forma rápida e isolada; Playwright valida comportamento observável pelo professor, com custo de execução maior mas cobertura de ponta a ponta.

## Engenharia como parte da confiança do produto

No ProfResolve, testes e observabilidade não são apenas preocupações técnicas. Fazem parte da estratégia para manter a plataforma confiável enquanto novas funcionalidades são desenvolvidas.

A combinação de testes automatizados, TypeScript estrito, logging estruturado e Sentry ajuda a identificar regressões, investigar falhas e reduzir riscos durante a evolução do produto.

Em operações críticas, como créditos e pagamentos, a idempotência ajuda a evitar processamentos duplicados durante tentativas repetidas de uma mesma operação. São decisões de engenharia que protegem a experiência do professor e contribuem para a confiabilidade do negócio.
